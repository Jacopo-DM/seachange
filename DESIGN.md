# Design

## Specs

Approved by the user on 2026-10-21. Goal numbers refer to PLAN.md. Goal 6 (api-cleanup) gets its spec once goals 1 to 5 are done.

### Goal 1: restart-guard

- `EA.restart` (in `EA.__init__` until T23) resolves the restart source and the target database (`db_file_path`, or `config.db_file_path` when it is `None`). If both name the same file, it raises `ValueError` naming the path and suggesting `db_file_path=`, before any database is opened.
- The check runs in both `db_handling` modes. In `"halt"` mode, this one case now raises `ValueError` where ARIEL raises `FileExistsError`.
- Acceptance: `ValueError` in both modes; the source file's bytes are unchanged afterwards; a relative and an absolute path to the same file are caught.
- Must not regress: restarts with a separate `db_file_path` (`tests/test_ea_restart.py`).

### Goal 2: floats-size-none

- `FloatsGenerator.uniform`, `normal` and `lognormal` return a plain `float` when `size=None`, as numpy does.
- Typing overloads on those three, `IntegersGenerator.integers` and both `choice` methods: `size=None` gives `float` or `int`, an `int` size gives a sequence. A `Sequence[int]` size (a numpy shape) keeps its current annotation.
- Acceptance: Hypothesis tests of the return type and length; the three `known bug` ignores removed; `ty check` reports 0 diagnostics.
- Must not regress: `tests/test_generators.py`.

### Goal 3: docs-build

- `docs/conf.py` loads `sphinx.ext.todo`, so the `Todo` section of a numpy docstring renders. Reversed 2026-10-22 (goal 10, R3): the empty section is gone and so is the extension.
- Acceptance: `sphinx-build -W --keep-going -b html docs docs/_build/html` exits 0.

### Goal 4: examples-tested

- `tests/test_examples.py` runs each example in a fresh interpreter (`subprocess`, `sys.executable`) with a temporary folder as the working directory. Not `runpy`: inside the suite the shared generator's state depends on earlier tests, so an in-process run could vary. (When T4 was written, `config.output_folder` was also fixed at import and an in-process run would have written to the repo's `__data__/`; T14 removed that.)
- `examples/a0_hello_world.py`, the empty `uv-cr-lib` template, is deleted (user, 2026-10-21).
- Acceptance: `a1_one_max.py` prints `best fitness 20.0 of 20` (deterministic: the generators use the fixed `SEED`). Coverage stays at 100%.

### Goal 5: close-connections

- `EA.restart` (in `EA.__init__` until T23) disposes the engine it opens on the restart source. The `dispose_engines` fixture in `tests/conftest.py` records every engine the package creates during a test and disposes them afterwards; test modules that build an `EA` or `Archive` opt in with `pytestmark`.
- Acceptance: `pytest.ini` turns `ResourceWarning` and `pytest.PytestUnraisableExceptionWarning` into errors, and every test passes. (Corrected from `-W error::ResourceWarning` alone, which could not fail; see Gotchas.)
- A public way for users to close a run (`close()` or a context manager) is a goal 6 candidate, not part of this goal.

### Goal 7: release-0.1

- Licence GPL-3.0-or-later, as ARIEL (copyright 2025 Jacopo Michele di Matteo and Ioannis Grigoriadis); `LICENSE` copied from ARIEL and `license = "GPL-3.0-or-later"` in `pyproject.toml`.
- `CHANGELOG.md` lists every change from `ariel.ec`, including goal 6's renames, as the migration note for ARIEL.
- Acceptance: `uv build` makes a wheel and an sdist; an isolated temporary environment installs the wheel and runs the README example, which reaches fitness 20 (the README version prints the genotype; `examples/a1_one_max.py` prints `best fitness 20.0 of 20`); goal 3 passes; the README and `[project.urls]` carry the repository URL.

### Goal 8: genotype-storage (approved 2026-10-21, met 2026-10-21)

Why: a numpy array genotype cannot be stored today (assigning one crashes in the setter with numpy's "truth value of an array is ambiguous"; a list of `np.int64` is accepted and the save then fails with `StatementError ... int64 is not JSON serializable`), and a list of floats is stored as JSON text, which costs 0.52 s of a 0.57 s generation at 100 × 10,000 weights (PLAN.md Baseline). The user: a genotype that goes in as a numpy array should come back as one; every genotype is kept by default; the release waits for this.

- A codec turns one kind of genotype into bytes and back. `GenotypeCodec` is a `Protocol` with `name: str`, `encode(genotype) -> bytes` and `decode(data: bytes) -> genotype`. seachange ships `json` (lists, dicts, strings and numbers, as today) and `numpy` (a short header with dtype and shape, then `array.tobytes()`; decoded with `np.frombuffer`). A PyTorch tensor needs a small user codec over `tensor.numpy()`; seachange does not depend on torch.
- Each stored genotype carries its codec's name (changed during T28 from one `RunInfo` table per run; see Decisions). The column type `codecs.GenotypeColumn` does all of it, so `EA`, `EA.restart` and `Archive` hold no codec code. Since goal 12 the column is `GenotypeRow.data` in the `genotype` table, and reading goes through `codecs.read_stored`, the column's own decoding, called by `individual.load_genotypes` and `GenotypeSource.read`. Worked cycle: `ind.genotype = np.array([1.5, 2.5], dtype=np.float32)` keeps the array in memory; when SQLAlchemy writes the row, the column asks `codec_for`, gets `NumpyCodec`, and stores `numpy`, a zero byte, then the `.npy` bytes (128 bytes of header, 8 of values); when `EA.restart` or `Archive` reads the row, the column splits off `numpy`, finds the codec with `codec_named` and returns a float32 array of shape `(2,)`.
- The run picks its codec by itself (user, 2026-10-21): each codec says which genotypes it handles (`handles(genotype) -> bool`); each genotype is stored by the first automatic codec that handles it, falling back to `json`. `EA(pop, ops)` with numpy genotypes therefore uses `numpy` with no argument. Adding an automatic codec must stay easy (user): `seachange.register_codec(codec)` appends one, such as a torch codec, without touching `EA`; a reader must register it too before opening the file, or the row reports `no codec named 'torch'`. There is no `codec=` argument (dropped in T28).
- mypy knows the exact genotype type (user, 2026-10-21): `Individual` becomes generic over it, as in `Individual[NDArray[np.float32]]`, so `parent.genotype + noise` type-checks without an `isinstance`. If SQLModel's table classes cannot take a type parameter cleanly, the work stops for a question.
- A genotype is set once and never changed (user, 2026-10-21: mutation makes a new genotype for the child; nothing edits one in place). So each genotype is encoded once, at its first save, and later saves cost nothing for it. An assigned numpy genotype is marked read-only (`flags.writeable = False`), so an accidental in-place edit raises at once: after `child.genotype = parent.genotype`, the line `child.genotype += noise` would otherwise change the parent's weights in memory and never reach the database. Marking it read-only also affects the caller's own array object; copying instead was rejected because it doubles the memory for every new genotype.
- Files written before goal 8 (by seachange 0.1 development or ARIEL) hold JSON text in `genotype_`; the column reads text as JSON. A stored value no codec can read becomes an `UndecodableGenotype` record. Since goal 12, `load_genotypes` (the engine and `EA.restart`) reports it with its row id (`Database row 2 is not a valid Individual: its genotype cannot be decoded: ...`), and reading `ind.genotype` of an `Archive` individual raises `ValueError: genotype of row 2 cannot be decoded`.
- Tags stay JSON: they are small labels, read and written by `Archive` filters.
- `NumpyCodec` writes a complete `.npy` file (`numpy.lib.format.write_array`, `allow_pickle=False`) rather than a home-made header plus `tobytes()`: dtype, shape, byte order and memory order are numpy's own format, so any numpy reads a stored genotype back with `np.load(io.BytesIO(blob))`, without seachange. The header costs about 128 bytes per genotype (0.3% of 10,000 float32 weights). Arrays of Python objects are refused: storing them needs pickle. Decoded arrays are read-only.
- `GenotypeCodec` is not generic: `encode` takes `object` and `decode` returns `object`, and each codec checks the type itself. A generic protocol is invariant in its genotype type (it takes and returns it), so codecs of different kinds could not share one list of automatic codecs. Exact typing comes from `Individual` (T30), not from the codec.
- Codecs are found newest registered first, then `numpy`, then `json`; `codec_for` falls back to `json` when none handles a genotype, and `json` then refuses a non-list with `TypeError`. A name can be registered once, as a stored name must point at one codec.
- Acceptance: PLAN.md goal 8's measure. Must not regress: every existing test, the one-max example (`best fitness 20.0 of 20`), loading a database written by today's code.

## Decisions

- 2026-10-21: copy, not move. seachange starts as a copy of ARIEL's `ariel.ec` engine; ARIEL keeps its own and does not depend on seachange. Chosen by the user: nothing in ARIEL breaks. The cost is that the two copies drift.
- 2026-10-21: scope is the engine (`EA`, `EAOperation`, `Individual`, `Population`, `Archive`, `Crossover`, settings, database) plus `generators/` and `optimizers/`, everything in `ariel.ec` that imports no robot code. ARIEL's genotypes (tree, CPPN, NDE) build robot bodies and stay there.
- 2026-10-21: the name comes from Ariel's song in The Tempest ("doth suffer a sea-change / Into something rich and strange"), close to what mutation does to a genotype, and it contains "ea". Free on PyPI on that date. Kept on 2026-10-23 (user), after doubts raised on 2026-10-22; still free on PyPI that day (404 from the JSON API and the simple index). `eabyss` (EA plus abyss) was the alternative considered: rejected because its pronunciation is unclear, it is easy to mistype, and an abyss is where things are lost, the opposite of a store that keeps every individual.
- Storage: every individual is a row in SQLite through sqlmodel and sqlalchemy, so a run can restart from any recorded generation. Settings come from pydantic-settings. Reason as in ARIEL, not recorded there.
- 2026-10-21: seachange is for researchers installing it from PyPI, and later for ARIEL, which will remove its own `ariel.ec` and import seachange. Chosen by the user. The public interface may change before 0.1; each change needs the user's approval and a line in the CHANGELOG mapping the `ariel.ec` name to the new one.
- 2026-10-21: until 0.1, seachange does not take ARIEL's robot genotypes or support databases other than SQLite. Both are planned for after 0.1 (user).
- 2026-10-21: the licence is GPL-3.0-or-later, as ARIEL, because the code is copied from ARIEL and relicensing needs every copyright holder's consent (user).
- 2026-10-21: restarting onto the source file raises `ValueError` in every `db_handling` mode (user). One rule with one message beats keeping halt's generic `FileExistsError` for this case.
- 2026-10-21: `size=None` returns a plain number, matching numpy, with typing overloads so a default `size=1` caller still gets a sequence type (user). The integer generators get the same overloads.
- 2026-10-21: the fitness direction has one name everywhere, `direction: Literal["max", "min"]` (user, goal 6 C10). A boolean `maximise=` was rejected: `sort(maximise=False)` reads as "do not maximise" rather than "ascending".
- 2026-10-21: a restart is `EA.restart(source, operations, *, generation=None, ...)`, and `EA(population, operations)` requires both (user, goal 6 C12). It makes a new run and a continued run two separate calls, which drops the `None` placeholder and the "either population or restart" error. The user accepted the migration cost because C10 and C2 already change ARIEL's calls.
- 2026-10-21: after `seed(n)`, a whole run repeats exactly: every random choice seachange makes follows it (user). Leaving `seed()` to the numpy generator only was rejected: a run whose selection uses `population.sample` would still differ from run to run.
- 2026-10-21: a restart continues from the individuals still alive at the end of the chosen generation, not everyone who lived through part of it (user). Keeping ARIEL's query was rejected: on one-max it restarted with 30 instead of the 20 the run had.
- 2026-10-21: the public repository is `https://github.com/Jacopo-DM/seachange` (user). The CI and docs workflows already target GitHub Actions; the repo can move to an org later.
- 2026-10-21: `LICENSE` carries two copyright lines: 2025 for the ARIEL code (Jacopo Michele di Matteo and Ioannis Grigoriadis) and 2026 for the seachange changes (Jacopo Michele di Matteo). Chosen by the user.
- 2026-10-21: the docs build fixes the `Todo` directive by loading `sphinx.ext.todo`, not by deleting the empty template sections (user). Reversed 2026-10-22 (user, goal 10 R3, asked again with this decision quoted): the empty `Notes` and `Todo` sections are deleted from `revde.py` and `docs/conf.py` matches the template, one approved difference fewer.
- 2026-10-21: `Archive.fitness_stats` returns a frozen `FitnessStats` and `generation_range` a frozen `GenerationRange`, both on one shared base class `seachange.model.Model` (`frozen=True`, `extra="forbid"`), as the Python standard asks for records (user, compliance check 9). Reason: `stats.mean` gets editor completion and mypy catches `stats.maen`; `stats["maen"]` only fails when it runs. Done before 0.1, so no outside caller breaks.
- 2026-10-21: rows read from a database file are validated as they load, in `EA.restart` and every `Archive` query, through `individual.check_rows` (user, compliance check 10). Reason: a SQLModel `table=True` model does not validate what it loads, so a file edited by another tool loaded a text `fitness_` such as `'high'` and failed later, far from the cause. A run's own per-generation fetch (`EA._fetch`) is not checked: it reads only what the run just wrote, and checking it would cost time every generation.
- 2026-10-21: the settings (`seachange.config` and the generator `settings`) are read-only (`frozen=True`), as the Python standard asks (user, compliance check 9). Reason: `config.direction = "min"` in one notebook cell changed every `EA` created afterwards, and nothing in the `EA(...)` line showed it; an ARIEL example comment shows it surprising someone. A run takes its values as `EA` arguments or from `SEACHANGE_` environment variables. Keeping them changeable as an approved exception was rejected for that reason; the cost is one line in ARIEL's Ackley notebook (`config.is_maximisation = False` becomes `direction="min"` on `EA`).
- 2026-10-21 (T28, deviation from the approved goal 8 spec, reported to the user): each stored genotype starts with its codec's name, instead of one `RunInfo` table per run, and `EA` has no `codec=` argument. Reason: SQLModel cannot hold a decoded genotype beside its bytes on rows it loads (Gotchas), so encoding and decoding moved into a SQLAlchemy column type, which sees one value at a time and no run. The cost is the name per row, 6 bytes for `numpy` against 40,000 bytes of weights. In return `EA`, `EA.restart` and `Archive` needed no change, and a run may mix kinds of genotype. `codec=` would only have forced a codec other than the automatic one, which no one has asked for.
- 2026-10-21 (T30): the genotype type `G` is a type parameter of `Individual`, `Population`, `Operation`, `EAOperation`, `EA` and `Archive`, with the default `Genotype`, so code that names no type is unchanged. `Individual.__class_getitem__` returns the class itself: otherwise pydantic builds a subclass for each `Individual[X]` (Python 3.13 evaluates function annotations when the function is defined) and SQLModel tries to make a second `individual` table. `Operation` asks for a plain `run` method instead of `__call__`, because mypy matched `EAOperation`'s overloaded `__call__` against the generic protocol and read the population as a bound argument whenever the operations were listed inline in `EA(...)`, the form the README uses. `EA.restart` became a static method with its own type parameter, because ty fills a class method's class parameter with its default on the bare class instead of reading the operations. Crossover returns arrays for array parents, because a list child cannot be assigned to an `Individual[NDArray]`.
- 2026-10-21: `Individual` stays a mutable SQLModel table, an allowed exception to "every record is a frozen model" (a type a third-party API forces): SQLAlchemy saves a row by changing it. The reason is a comment at the class.

- 2026-10-22: functional notebooks (goal 9). Six, one per feature area, chosen by the user: engine, archive, genotypes, generators, crossover, revde. matplotlib is a dev dependency for their plots (user): a fitness curve shows a stalled run at a glance, where a printed table has to be read. The coverage table has one row per public module of `seachange`, not per feature area, so `tests/test_functional_notebooks.py` can compare it with `pkgutil.iter_modules` and fail on a new module without a row. Each notebook builds its own run and data instead of reading another notebook's file, because the runner gives each notebook its own temp folder and runs them in any order. No notebook needs a display, GPU or network, and none is marked slow (each runs in 2 to 3 s).
- 2026-10-22: `generators.ipynb` uses seed 19, picked by replaying the notebook's draws for seeds 1 to 59, because at seeds 11 and 12 one of `inversion` or `scramble` happened to return an unchanged child and the table showed nothing. The notebook says why the seed was chosen and measures how often a child comes back unchanged.
- 2026-10-23 (user): restarts and which genotypes a run keeps, built as goal 11 (b35ce2e, 2efd896, 52a0d49). (1) `EA.restart(source, ops, generation=g)` stores the survivors as generation g, not g + 1, so a run restarted from 10 for 20 steps writes 11 to 30 and its numbers match the original's. (2) The restarted file gets the source's whole history up to g: every individual born by g, with its id kept and its death capped at g, and every genotype the source kept, so the file answers every question on its own. The copy costs disk space, not run time: about 45 MB at the goal 8 sizes and 0.2 s at the measured 200 to 300 MB/s; a `step()` reads only the living population. (3) A setting `keep_genotypes` decides which genotypes a run keeps after their individual dies: `"all"` (the default, today's behaviour), or any subset of `["best", "median", "worst"]`, meaning those individuals of each generation, ranked by fitness under `direction` among the evaluated individuals present in it, with median as in `EA.get_solution`; `[]` keeps only the living population. The living population's genotypes always stay, because every `step()` reads them. A dropped genotype's individual keeps its row (fitness, birth, death, tags), and reading the genotype raises a clear error. Only `"all"` can restart from a generation before the latest. Example, 4 MB genotypes, 100 new per generation, 1,000 generations: `"all"` about 400 GB, `["best", "median", "worst"]` about 12 GB, `["best"]` about 4 GB, `[]` about 400 MB.
- 2026-10-23 (user, house-keeping): the JSON type aliases change in 0.2: the `genotype` and `tags` setters convert on assignment, tuples to lists and dict keys to strings, so `ind.genotype = (1, 2)` reads `[1, 2]` at once and the value no longer changes on its way through the database; `JSONIterable` and the dict alias narrow to lists and string keys. Not built yet (PLAN.md Tasks).
- Replaced the same day by the next entry. 2026-10-23 (user said no preference; Claude picked): WAL and `synchronous=NORMAL` wait for the first goal with several writers. Reason: seachange has one writer per file, which commits once per generation, so the default settings cost nothing measurable there; WAL adds `-wal` and `-shm` files beside every database and does not work on network filesystems, where cluster runs often write. Measured limits in Results (storage limits) and `docs/limits.md`.
- 2026-10-23 (user, approving goal 13): databases open with `journal_mode=WAL` and `synchronous=NORMAL`. Reason: on the Lenovo the disk sync of each generation's commit is about 10 ms of the 35.9 ms a small-genome generation costs (25.6 ms with WAL and NORMAL, measured by switching them on from outside). Cost, accepted: a power cut can lose the last commit or two, though the file stays intact; every open database has `-wal` and `-shm` files beside it; a run on a network filesystem must write to a local disk.
- 2026-10-23, goal 13 (T35): `individual.save_individuals` assigns new individuals' ids itself, the largest id in the file plus one, in population order, keeping a given id (a restart's survivors). Reason: SQLAlchemy runs an `INSERT ... RETURNING id` with `sort_by_parameter_order=True` as one statement per row on SQLite, because SQLite does not promise the order of a multi-row `RETURNING`; assigning the ids lets one `executemany` insert the generation, and gives the numbers SQLite would, since the run's engine is the file's only writer during a commit. Stored individuals get one `UPDATE` per set of changed columns, read from `InstanceState.unmodified`, so a dict changed in place (`ind.tags["k"] = 1`) stays unsaved, as with the ORM. After the commit, `individual.mark_saved` marks each written individual as stored with `make_transient_to_detached` (after `make_transient` for one already stored, as the call takes only an individual with no key), so a second save of the same object updates it instead of inserting it again (found by `tests/test_saving.py::test_new_individuals_get_ids_in_population_order`) and an updated column is not written again until it is assigned again (every stored individual assigned to since its last save is cleared, written or not, as the ORM's flush clears every object it is given). The `UPDATE` finds a row by the id in the individual's key, not its current `id`, so a changed id moves the row as the ORM's `UPDATE ... SET id` did, and a taken id fails with `IntegrityError` instead of overwriting another row. An individual is new when SQLAlchemy has no key for it (`individual.is_new`), not when its id is `None`. The errors are the ORM's: an `UPDATE` that matches fewer rows than it was given raises `StaleDataError`, two objects with one key raise `InvalidRequestError`, and `EA._commit` gives new individuals back the ids they had when the commit fails. The genotypes follow the same rule: `save_genotypes` and `drop_genotypes` only write, and `mark_genotypes_saved` marks them saved, or forgets the dropped ones, after the commit (fixed 2026-10-24; before, a commit that failed late left a genotype counted as saved, so the next commit stored its row without it, on 0.1.0 too).
- 2026-10-24 (user, house-keeping): individuals drawn from `Archive` are saved into a new run as new rows. Reason: `Archive` already cleared their ids for that purpose (its comment says so), but SQLAlchemy kept the old file's key, so saving them raised `StaleDataError`, on 0.1.0 too; `_read_genotypes_later` now calls `make_transient` as well. A behaviour change, approved by the user. They are born in the generation they are first saved there (`EA._commit`, for an individual that is new and `from_another_file()`), and those in a new run's starting population are made alive in `EA.__init__`, as `EA.restart` treats survivors (user, 2026-10-24: a dead draw would otherwise never take part, and its birth would name the old run's generation). A draw an operation adds keeps the `alive` the operation set, since an operation may add and retire it in one step. `from_another_file()` reads a private `_drawn` mark that `read_genotype_from` sets and only `mark_saved` clears, so a draw given a new genotype is still recognised. `EA` reads the genotypes of its starting population's draws before `setup_database` replaces the file they come from, since the default path makes that likely; for a draw read later, `setup_database` writes a random identity into the file's `PRAGMA user_version` and `GenotypeSource.read` refuses a file whose identity differs from the one `Archive` saw (a deleted and recreated file can reuse the inode, and the modification time changes with every commit, so neither can tell the files apart). Found by two reviews of the change, each case with a test in `tests/test_saving.py`. An individual saved by one run and put in another's population joins that run the same way (`Individual.leave_other_run`, 2026-10-24, the user's choice of "saved there"): `mark_saved` and `EA._fetch` stamp each row with the identity of the file that holds it (`_stored_in`), and a row stamped by another file becomes new, with its genotype marked unsaved. Before, its key from the first file made the second run treat it as stored, so it was written nowhere, or overwrote the second file's row of the same id.

## Rejected approaches

- Making ARIEL depend on seachange at the time of the copy (one copy of the engine). Rejected by the user then, in favour of leaving ARIEL untouched; on 2026-10-21 the user planned it for after 0.1 (see Decisions).
- Restart onto its own source file: writing the new run under a derived name such as `database_restart.db`. Rejected: the user may not notice where the data went. Checking inside `setup_database` was also rejected, because it does not know about restarts.
- `size=None`: returning a one-item list (rejected by the user; it breaks numpy's convention), or annotating the return as a plain union (every caller would have to narrow, even with the default `size=1`).
- Docs build: deleting the empty `Notes` and `Todo` sections from `revde.py`'s docstring. The user chose to enable `sphinx.ext.todo` instead. No longer rejected: done 2026-10-22 (goal 10, R3).
- `operations` required (C12): keeping the `None` default (the mistake already fails at once) or dropping both defaults (restarts would still read `EA(None, ops, restart=...)`). Both rejected in favour of `EA.restart()`.
- Licence: relicensing under MIT or similar. It needs written consent from every copyright holder of ARIEL's code.
- Moving this repo's template differences (`pytest.ini`'s leak filter, and until 2026-10-22 `docs/conf.py`'s `sphinx.ext.todo`) into the shared templates in `~/Functions/_rsync/`. The user kept them in this project only (recorded in CLAUDE.md); in the templates, the leak filter would fail other projects that leak resources.
- `Archive` draws: keeping SQLite's `ORDER BY random()` (it cannot be seeded, so `seed()` could not repeat a run), or loading every matching row and sampling in Python (loads whole archives). `_draw` reads only the ids in id order, samples them with `py_rng`, then loads the picked rows.

- Restart history and genotype modes, rejected 2026-10-23 (user): copying only stubs (rows without genotypes) or linking to the source file in place of the full copy (stubs save space but fail on a dead ancestor's genotype; a link breaks when the source moves); a `best_only` mode, in all three readings (the single best of the run, the best of the final generation, the best of each generation alone), dropped by the user in favour of the best, median and worst subset; fixed named modes (`all`, `best_of_each_gen`, `alive_only`, `best_only`) in place of free combinations. Compression is not a way to shrink the copy: evolved float32 weights keep 89 to 93% of their size (Genotype storage, below).

- Goal 13 (T35), rejected 2026-10-23: inserting the generation's genotypes as one multi-row `insert(GenotypeRow).values(list)` (SQLAlchemy compiles a new 150-row statement every generation; an `executemany` of one statement is used instead), and `INSERT ... RETURNING` for the new ids (one statement per row on SQLite, see Decisions). Batching alone cut the commit only from 21.3 to 16.8 ms: per-statement overhead was not the main cost; the disk sync (about 10 ms) and building and tracking objects were.

- Genotype storage, measured 2026-10-21 (scratch scripts; plain `sqlite3`, 100 float32 genotypes of 10,000 weights, so without SQLAlchemy's own cost): JSON text writes in 0.33 s and reads in 0.19 s at 20.7 MB; raw bytes in the database 0.003 s and 0.002 s at 4.1 MB; one `.npy` file per genotype 0.006 s and 0.005 s at 4.0 MB. At 1,000,000 weights JSON took 37 s to write, raw bytes 0.25 s. Chosen for goal 8: raw bytes in the database.
    - JSON text for arrays: rejected, about 100 times slower and 5 times larger than raw bytes, and it loses dtype and shape.
    - `.npy` files beside the database: as fast as raw bytes, rejected because the folder and the database can drift apart (a deleted or uncopied file breaks a restart).
    - Pickle: round-trips any object with no codec, rejected because only Python can read the file, existing databases would not load, and opening someone else's database can run code hidden in it.
    - HDF5 (h5py), zarr or npz files beside the database, raised by the user on 2026-10-21: not measured, by the user's choice, and kept out of goal 8. Raw bytes in SQLite already store 100 genotypes in about 3 ms, so a second file can save little time, and it splits a run in two: a crash between the two writes leaves records and weights that disagree, and restarts, `Archive` and copies need both files. HDF5 is the one worth adding later, for reading one weight across a whole run or opening runs from other languages, as a second storage backend (PLAN.md After 0.1), not as a codec. zarr adds two dependencies and a folder of many small files; npz cannot be appended to.
    - A type tag on every value, so one run can mix kinds of genotype: rejected in the goal 8 proposal for its cost per row, then chosen in T28 when that cost turned out to be the codec name, about 6 bytes (see Decisions).
    - One `RunInfo` table per run naming its codec, as first specified: dropped in T28 (see Decisions).
    - General compression of one genotype (10,000 float32, 40,000 bytes): zlib keeps 92.9% (1.2 ms), byte shuffle + zlib 88.7% (1.4 ms), lzma 92.5% (21 ms). Evolved weights look random, so it saves about 11% for a write about 30 times slower than raw bytes; rejected.
    - float16: half the size in 0.04 ms, but it rounds every weight, so the stored network is not the one evaluated. Left for a later opt-in codec, never a default.
    - A child stored as the XOR of its bits with its parent's, then zlib: 14.1% of raw when mutation changes 10% of the weights, 73.2% (with byte shuffle) when it nudges all of them. Deferred, not rejected: reading a genotype means rebuilding it from its ancestors, crossover children have two parents, and one bad row breaks every descendant.

## Gotchas

- The dependency versions are newer than ARIEL's lock (numpy 2.5.4, sqlalchemy 2.1.6, sqlmodel 0.0.48 against 2.3.3, 2.0.43, 0.0.27). numpy 2.5's stubs are what exposed the `size=None` crash (fixed by T6).
- A SQLite connection that the garbage collector closes raises its `ResourceWarning` inside `__del__`, where pytest catches it as an unraisable exception and reports `PytestUnraisableExceptionWarning`. So `-W error::ResourceWarning` alone never fails a test for a leak; `pytest.ini` turns both into errors. The failure is reported on whichever test is running when the collector runs, often the test after the leaking one.
- ruff bans `autouse=True` fixtures (`pytest-fixture-autouse`). Shared setup is opted into per module with `pytestmark = pytest.mark.usefixtures(...)`.
- Changing an individual's `tags` (or `genotype`) dict in place, as in `ind.tags["k"] = 1`, is not saved: the JSON columns do not track changes inside the value, so only assignment reaches the database. Checked 2026-10-21 with a two-generation run: the in-place tag was gone in the archive, the assigned one was there.
- `uv-cr-lib`'s template `tools/run_notebooks.py` fails mypy unless `nbclient`, `nbformat` and `ipykernel` are installed. They are in the dev group here, so `uv sync --all-groups` covers it.
- `uv run --isolated --offline --with dist/<wheel>` fails to resolve seachange's dependencies even though their wheels are in uv's cache; it needs network to pypi.org for the index listings (checked 2026-10-21). `uv pip` would avoid the resolver, but the user's python-guard hook blocks it.
- `uv_build`'s sdist contains a `pyproject.toml.orig` next to `pyproject.toml`; the repo has no such file.
- `Archive` sets `id = None` on every individual it returns (`_fetch_all`, `_draw`), so they can be added to a new run as new rows. Tests that compare draws must compare genotypes, not ids: comparing ids compares `None` with `None` and always passes.
- Hypothesis tests cannot use pytest's `tmp_path`: a function-scoped fixture is shared by every generated example. `tests/test_round_trip.py` makes a `TemporaryDirectory` per example instead.
- `statement.with_only_columns(...)` turns sqlmodel's `SelectOfScalar` into a plain SQLAlchemy `Select`, which sqlmodel's `Session.exec` does not accept under mypy; `Archive._draw` uses `session.scalars(...)` for the id query.
- `mypy.ini` sets `warn_unreachable`, so a `match` over a `Literal` with a `case _:` fallback is reported as unreachable. `EA.get_solution` checks the mode with a guard before the branches instead.
- `numpy.generic` takes its item type only in numpy's stubs: `NDArray[np.generic[object]]` is what mypy accepts without an explicit `Any` (plain `NDArray[np.generic]` is `generic[Any]`), but `np.generic[object]` raises `TypeError` when Python evaluates it. `codecs.Array` is therefore a `type` alias, whose value Python never evaluates.
- SQLModel sets `__pydantic_private__` to `None` on rows SQLAlchemy loads (`sqlmodel/_compat.py`, `init_pydantic_private_attrs`), so a pydantic `PrivateAttr` on a table model works on new objects and raises `TypeError: 'NoneType' object is not subscriptable` on loaded ones (checked 2026-10-21 with sqlmodel 0.0.48). Goal 12 keeps the genotype in private attributes all the same: a SQLAlchemy `load` event on `Individual` (`individual._start_private_state`) sets `__pydantic_private__` to the declared defaults on every loaded row; a plain assignment works, checked 2026-10-23.
- `GenotypeColumn` does not override `compare_values`, though `==` on two numpy arrays is ambiguous: SQLAlchemy did not compare old and new genotypes when `EA` replaced a stored array, nor when a loaded row's array was replaced inside one session (both checked 2026-10-21 with the default comparison). Since goal 12 this no longer arises: `Individual` has no genotype column, and `save_genotypes` writes changed genotypes with an explicit insert that replaces the stored row. `tests/test_ea.py::test_a_saved_numpy_genotype_can_be_replaced` still guards the `EA` path.
- A separately built list of operations, `ops = [EAOperation(a), EAOperation(b, 0.5)]` followed by `EA(population, ops)`, fails mypy when the operations bind different arguments: mypy joins `EAOperation[[], ...]` and `EAOperation[[float], ...]` to `object`. It failed before T30 too (checked on `master`); listing the operations inline in `EA(...)` works, or annotate `ops: list[Operation[G]]`.
- mypy narrows a property to the value just assigned: after `ind.genotype = [1.0]`, `ind.genotype` reads as `list[float]`, not `Genotype`. `tests/test_genotype_types.py` reads it back through a `Population` to see the declared type.
- vulture reports 10 "unused variable" findings at 100% confidence that are all parameters a signature forces: `exc_type`, `exc`, `traceback` of `EA.__exit__` and `Archive.__exit__`, `dialect` of `GenotypeColumn.process_bind_param` and `process_result_value`, `typevar_values` of `Individual.__class_getitem__`, and `factor` in `tests/test_ea_operation.py`, which exists to test binding. None is dead code (checked 2026-10-21 with vulture 2.16).
- Validating a loaded row with `Individual.model_validate(row.model_dump())` prints pydantic serializer warnings for a bad value; `model_validate(row, from_attributes=True)` validates without dumping first.
- `Archive.by_generation(g)` returns everyone present in generation g: the survivors and the individuals retired during g (born at or before g, `time_of_death == g`, `alive` false). With 20 survivors and 10 children a generation it returns 30. The survivors alone are `[m for m in archive.by_generation(g) if m.alive or m.time_of_death > g]`, the same filter `EA.restart` uses. Found while writing `tests/functional/archive.ipynb` (2026-10-22).
- For `FloatMutator.inversion`, `IntegerMutator.inversion` and `IntegerMutator.scramble`, `mutation_probability` is the chance that the one operation happens per child, not a chance per gene as in the other mutators. Even at probability 1, a child of 20 genes comes back unchanged about one time in six, when the two cut points (among 21 gaps) enclose one or two genes: 175 of 1,000 measured at seed 11 (2026-10-22).
- A genotype no codec stores (a frozenset with no codec registered) fails when the individual is saved, inside SQLAlchemy, so it reaches the caller as `sqlalchemy.exc.StatementError`; the codec's `TypeError` (`JsonCodec stores lists and dicts, not <class 'frozenset'>`) is its `.orig`.
- ty checks the notebooks in `tests/functional/`; mypy does not, and the pre-commit `ruff format` and `ruff check` hooks skip them (their `types_or: [python, pyi]` leaves out `jupyter`). The Stop hook's and CI's `ruff format --check` and `ruff check --no-fix` on `.` do cover notebooks, and so does `uv run --locked ty check`. An untyped `Individual()` given a frozenset or numpy genotype is a ty error in a notebook cell; annotate it `Individual[X]`.
- On Python 3.13, `slice[int, int, None]` in an annotation raises `TypeError: type 'slice' is not subscriptable` at import (the builtin takes type parameters at runtime only from 3.14), while a bare `slice` is `slice[Any, Any, Any]` to mypy and fails `disallow_any_explicit`. Quote it: `-> "slice[int, int, None]"`, as `generators/_shared.py` `cut_points` does; ruff accepts the quotes.
- A restarted file keeps the source's ids up to the restart generation only. Its new individuals take ids after the largest copied one, so they can reuse the ids of the source's individuals born after the restart: id 1500 in the two files is then two different individuals.
- `ea.py` grew to 689 lines with goal 11 and 742 with goal 12, and is now the largest file in `src` (it was 498, goal 10 skip S3 kept it whole); `individual.py` grew from 255 to 573 with goals 11 and 12.
- An `Archive` individual reads its genotype from the file when first asked for (`GenotypeSource`), so it fails once the file is moved or deleted; `tests/test_round_trip.py` reads it inside the temporary folder for that reason. Pickling such an individual sends the source record, not the genotype, so a worker process reads it from the file too.
- SQLModel table models ignore unknown keyword arguments, so `Individual(genotype_=...)` silently sets nothing now that `genotype_` is a property, not a field.
- `dict(result)` on a SQLAlchemy result treats it as a mapping, because results have a `keys()` method, and fails; ruff's unsafe fix suggests it. Use `dict(result.all())`.
- A dropped genotype does not free all its space (measured 2026-10-23 with SQLite's `dbstat`, 100 generations of `keep_genotypes=[]` at the goal 8 sizes): the individual table had 10,100 leaf pages, one per individual, 98% unused. SQLite stores the first 4 KB of a large value in the row's leaf page and the rest in overflow pages; setting the genotype to NULL frees the overflow pages, which later genotypes reuse, but leaves the leaf page nearly empty, and new rows, with higher ids, never fill it. So a dropped individual costs about one 4 KB page whatever its genotype's size. Over 200 generations `[]` reached 91 MB and best, median and worst 108 MB (about 860 MB with `"all"`, extrapolated from 86 MB for 20 generations); `VACUUM` brought them to 5.9 MB in 0.09 s and 24.8 MB in 0.24 s. Goal 12 moved genotypes to a table of their own, where deleting a genotype row frees whole pages: the same `[]` run is 6.0 MB.
- `==` on two `Individual` objects compares their pydantic private attributes too, the in-memory genotype included, so it raises `ValueError: The truth value of an array ... is ambiguous` for numpy genotypes. Code that looks individuals up in a list (`ind in new`) must compare by identity (`id(ind)`), as `save_individuals` does.
- `setup_database` removes an old database's `-wal` and `-shm` files under `db_handling="delete"`, following SQLite's warning that a mismatched `-wal` can corrupt a file. The danger did not reproduce (2026-10-23): a copy of a live run with its `-wal`, replaced this way without removing the `-wal`, still gave a new file with only the new rows; `tests/test_saving.py::test_replacing_a_database_drops_its_old_journal` guards the outcome, not the cause.
- A fresh-eyes review of goal 13's batched save (2026-10-23) found six ways it differed from the ORM, each fixed with a test in `tests/test_saving.py`. The causes: `InstanceState.unmodified` counts a column assigned its own value as changed, where the ORM compares the values (`state.attrs[name].history.has_changes()` does); updated rows kept their change history, so a dict changed in place after one assignment was saved at the next commit; marking rows stored inside the transaction survived its rollback; nothing refused two objects for one row; an `Archive` row had `id = None` but kept its file's key, so it was not new (fixed 2026-10-24: `_read_genotypes_later` drops the key too); and a file in WAL mode needs a writable folder even to be read, because SQLite creates its `-shm` file on open (so `EA.close` calls `ea_database.leave_write_ahead`). The switch back fails with `database is locked` while an `Archive` is reading, after the 5 second lock wait, and with `disk I/O error`, not a read-only error, when the file is read-only; `leave_write_ahead` checks write permission first, waits for no lock, and leaves the file in WAL mode in both cases, so `close` never fails because the run is being read.
- `PRAGMA journal_mode=WAL` is stored in the database file, `synchronous` is not: it is set on every connection, by the `connect` event `ea_database._write_ahead` attaches to a run's engine. `Archive` and `EA.restart`'s reading engines open files with the default `synchronous`.
