## Known problems

- The JSON type aliases promise more than a JSON column keeps: `JSONIterable` allows a tuple, which comes back as a list, and `dict[Hashable, ...]` allows non-string keys, which come back as strings (`{1: "a"}` returns as `{"1": "a"}`). Checked 2026-10-21. Fixing it means narrowing the aliases to lists and string keys (a typing change) or validating on save; not changed without the user's approval. Option found later: convert in the `genotype` and `tags` setters, so `ind.genotype = (1, 2)` reads back `[1, 2]` at once and the value never changes on its way through the database, with the aliases narrowed too. A storage format that keeps tuples was rejected: the column would stop being plain JSON and `Archive`'s queries get harder. Asked 2026-10-21; the user has not chosen yet. The question led to goal 8 instead ("genotype is a bit special"): numpy genotypes now round-trip exactly, but a tuple or a non-string key in a JSON genotype or in tags still comes back changed; `JsonCodec`'s docstring and `tests/test_codecs.py::test_json_codec_turns_tuples_and_number_keys_into_json` say so. Decided 2026-10-23 (user): convert on assignment, in 0.2 (DESIGN.md Decisions; task T33).
- Rows a user loads with their own SQLModel `Session` carry no file stamp (`Individual._stored_in`), so put in another run's population they are taken as that run's rows: one whose id is a dead row there overwrites it silently (a review's test set run B's row 3 to `fitness_` 999.0), one whose id is a living row raises `InvalidRequestError` (found 2026-10-24 by the review of the known-problems fixes; the same on `main`). `Archive` and `EA` stamp or clear what they load; a session of the user's own cannot. Fix: stamp rows in the `load` event from the connection's file, or goal 14's plain `Individual`, which makes this go away. Estimate: an hour; not started.
